Button Driver — Firmware Architecture
 
 
1. Purpose
 

 
The Button Driver provides a reusable interface for handling physical push buttons.
 
It is responsible for:
 
Reading the GPIO
 
Detecting possible transitions
 
Debouncing the mechanical switch
 
Maintaining the button state machine
 
Updating the stable state
 
Generating a press event
 
The application does not need to implement these details itself.
 

 
2. Button State Machine
 

 
The driver uses four states:
 
RELEASED
 
PRESS_DEBOUNCE
 
PRESSED
 
RELEASE_DEBOUNCE
 
Normal press sequence:
 
RELEASED
 
↓
 
PRESS_DEBOUNCE
 
↓
 
PRESSED
 
Normal release sequence:
 
PRESSED
 
↓
 
RELEASE_DEBOUNCE
 
↓
 
RELEASED
 

 
3. Press Detection
 

 
With INPUT_PULLUP:
 
Released:
 
HIGH
 
Pressed:
 
LOW
 
Therefore the driver interprets:
 
digitalRead(button.pin) == LOW
 
as a pressed button.
 

 
4. Debounce Process
 

 
When a possible press is detected:
 
The driver enters PRESS_DEBOUNCE.
 
The current time is stored.
 
The button must remain pressed for the debounce period.
 
After the required time:
 
The press is accepted.
 
The state becomes PRESSED.
 
stablePressed becomes true.
 
pressEvent becomes true.
 
If the button is released before confirmation:
 
The transition is cancelled.
 

 
5. Release Debouncing
 

 
The same concept is used when releasing the button.
 
When the driver detects a possible release:
 
The state becomes RELEASE_DEBOUNCE.
 
The current time is stored.
 
The button must remain released for the debounce period.
 
After confirmation:
 
The state becomes RELEASED.
 
stablePressed becomes false.
 
If the button is pressed again before confirmation:
 
The driver returns to PRESSED.
 

 
6. Raw State
 

 
The raw GPIO state is read directly from the hardware.
 
Example:
 
bool pressed = (digitalRead(button.pin) == LOW);
 
This value can change rapidly during mechanical bounce.
 

 
7. Stable State
 

 
stablePressed represents the state accepted by the driver after debounce.
 
It should only change after the state machine confirms the transition.
 
This prevents electrical noise and mechanical bounce from becoming application-level behavior.
 

 
8. Press Event
 

 
pressEvent represents a transition rather than a persistent condition.
 
It is set to true only when a new press has been confirmed.
 
At the beginning of every update:
 
button.pressEvent = false;
 
After a valid press:
 
button.pressEvent = true;
 
This means the event exists for one processing cycle.
 
A button that remains physically held does not continuously generate press events.
 

 
9. Struct
 

 
Each button stores its complete runtime state inside a Button structure.
 
Fields:
 
pin
 
Hardware pin number.
 
state
 
Current state of the state machine.
 
debounceStart
 
Timestamp used for debounce timing.
 
stablePressed
 
Debounced button state.
 
pressEvent
 
One-cycle press event.
 

 
10. Reference
 

 
The driver update function receives the Button object by reference:
 
void updateButton(Button &button)
 
The reference is necessary because the function modifies the original Button object.
 
The modified state must remain available after the function returns.
 

 
11. Multiple Buttons
 

 
Multiple Button objects are stored in an array:
 
Button buttons[BUTTON_COUNT];
 
The same driver function processes every button:
 
for (uint8_t i = 0; i < BUTTON_COUNT; i++) { updateButton(buttons[i]); }
 
This avoids duplicating the debounce and state-machine implementation.
 

 
12. Application Layer
 

 
The application uses events generated by the driver.
 
Example:
 
if (buttons[0].pressEvent) { ledState = true; }
 
if (buttons[1].pressEvent) { ledState = false; }
 
The Button Driver does not decide what the LED should do.
 
It only reports the event.

14. Engineering Principle
 

 
The main principle demonstrated by this project is separation of responsibilities.
 
The Driver knows how the hardware works.
 
The Application knows what the system should do.
 
This makes the firmware easier to reuse, test, and expand.
 

 
15. Current Limitation
 

 
The current driver generates a press event.
 
Future versions can be extended with:
 
Release events
 
Long-press detection
 
Repeat events
 
Double-click detection
 
Multiple button event types
 
These features will be added only when they become necessary in later projects.
